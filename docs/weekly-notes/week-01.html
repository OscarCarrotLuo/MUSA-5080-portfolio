Week 1: Getting Set Up

Quarto, project files, Git, GitHub, and the portfolio publishing workflow.
Published

August 28, 2026

What We Did

We set up the portfolio workflow: created a repository from a template, cloned it with GitHub Desktop, edited source files in RStudio, rendered the site with Quarto, and published the output through GitHub Pages.

Key Concepts

  • A website needs files, usually HTML, and a server that makes those files available online.
  • Quarto converts .qmd source files into .html pages.
  • Saving a source file, rendering a site, committing a snapshot, and pushing to GitHub are separate actions.
  • A .qmd file can combine YAML metadata, Markdown writing, executable R code, and rendered results.
  • Source files are edited by people; output and cache files are generated by tools.

Notes

1. What is a website?

In the class workflow, a website has two main parts:

a folder of HTML files + a server that is always online

For this portfolio:

Quarto creates the HTML files
GitHub Pages hosts those files online

The complete path from source to website is:

.qmd source file -> Quarto Render -> .html page -> GitHub Pages

I normally edit the .qmd source rather than the generated .html file.

2. Quarto and Render

Quarto is a publishing system that combines writing, code, and results in one document. It can render a .qmd file as a webpage, PDF, slide deck, or Word document.

When I select Render, Quarto:

  1. Reads the .qmd file from top to bottom.
  2. Finds executable code chunks.
  3. Sends R code to R and receives the results.
  4. Combines the writing, code, and output into HTML.

Saving only records edits in the source file. Rendering rebuilds the output page, so Save is not Render.

3. Anatomy of a .qmd file

A Quarto document normally contains three parts:

YAML header + Markdown text + R code chunks

YAML header

The YAML header goes at the very top and stores page metadata:

---
title: "Week 1: Getting Set Up"
description: "My first weekly note"
date: 2026-08-28
---

Important YAML rules:

  • The opening and closing --- lines matter.
  • A colon must be followed by a space.
  • Dates should use YYYY-MM-DD.
  • Use plain quotation marks.

Markdown

Markdown provides headings, paragraphs, lists, emphasis, and links:

## What I Learned

This is a paragraph with a [link](https://quarto.org/).

- First point
- Second point

R code chunks

An executable R chunk in a Quarto file uses an opening fence labeled {r}. The code inside a chunk might look like this:

library(tidycensus)

x <- 2 + 2
print(x)

R code should be placed inside a code chunk when I want Quarto to run it and include the result in the page.

4. Files and folders

A useful question is: Who is this file for?

Files I edit directly:

index.qmd
about.qmd
weekly-notes/*.qmd
assignments/*.qmd
_quarto.yml

Files and folders mainly used by software:

Item Purpose
.Rproj Opens the folder as an RStudio project
.gitignore Tells Git which files not to track
.Renviron Stores environment variables and secrets such as API keys
docs/ Contains the rendered website published by GitHub Pages
_freeze/ Stores Quarto execution results and cache data

The key rule is: edit source files and allow Quarto to regenerate output files.

5. Why index.qmd matters

Web servers normally look for index.html when a visitor requests a folder URL. Quarto creates that file from index.qmd:

index.qmd -> Render -> docs/index.html

That is why the portfolio homepage source file is named index.qmd.

6. Git, GitHub.com, and GitHub Desktop

These tools are related but have different roles:

  • Git is the version-control system running locally on my computer.
  • GitHub.com stores an online copy of the repository.
  • GitHub Desktop provides buttons and menus that send commands to Git.

Commit and push are also different:

Commit = save a labeled snapshot in the local Git repository
Push   = send local commits to GitHub.com

7. The portfolio workflow

Edit -> Save -> Render -> Commit -> Push -> wait -> refresh the live site

Each step changes a different version of the work:

  1. Edit and Save: update the local source file.
  2. Render: rebuild the local website output.
  3. Commit: record a labeled local snapshot.
  4. Push: transfer commits to GitHub.com.
  5. Refresh: check the published GitHub Pages site.

8. Markdown, R scripts, and Quarto documents

Markdown text = writing and formatting, without calculation
R script      = reusable code
.qmd document = writing + code + results

An R script is useful for experimenting with code and building reusable analysis. A .qmd document is useful when I need to explain the analysis and publish its results together.

Proving R Works

The chunk below reports the version of R used by the project. If the result appears on the rendered page, R and Quarto are communicating correctly.

sessionInfo()$R.version$version.string
[1] "R version 4.6.1 (2026-06-24)"

Reflection

This week helped me understand that building a reproducible website is a sequence rather than a single save button. I want to become more confident using R, Quarto, Git, and GitHub to create clear public-facing work. The number of separate steps still feels unfamiliar, but repeating the workflow should make it more natural.

Questions I Still Have

  • When should code live in an R script instead of directly in a .qmd file?
  • How does Quarto decide which output files need to be rebuilt?
  • How is a Quarto website different from a website written directly with HTML, CSS, and JavaScript?
